# v0.1 — PC and phone over Wi-Fi and USB networking

The phone runs a native ROS 2 Jazzy node named `robot_brain`, through the ROS C
client API (`rcl`) and Cyclone DDS. Kotlin owns the Android UI, permissions,
hardware adapters and lifecycle; C++ owns the ROS context, node and endpoints.
No PC bridge is needed. The PC's existing Fast DDS ROS installation is used
for interoperability testing.

v0.2 is phone-to-microcontroller communication over network and USB, including
the phone-hosted micro-ROS Agent. That Agent is not included in v0.1.

## Publishers

1. Open **ROS2 Android → Publishers**.
2. Filter **Motion**, **Cameras**, or **Other**, or view **All**.
3. Choose the capability you want to expose. Unavailable hardware is disabled.
4. Edit the absolute ROS topic, or use **Choose discovered topic** to select a
   discovered topic with the matching message type. Discovery may take a few
   seconds; retry if the list is initially empty. A new topic can be entered
   manually.
5. Set the maximum rate and tap **Publish**. The first endpoint starts the ROS
   session. The counter reports successful local ROS publish calls; the PC
   must be checked separately to establish delivery.
6. Tap **Stop** before editing an active endpoint. Multiple motion/environment
   publishers can run together. v0.1 allows one camera at a time.

| Capability | ROS type | Data convention |
| --- | --- | --- |
| Combined IMU | `sensor_msgs/msg/Imu` | Acceleration including gravity plus latest gyro sample; orientation unavailable |
| Accelerometer | `geometry_msgs/msg/Vector3Stamped` | m/s² |
| Gyroscope | `geometry_msgs/msg/Vector3Stamped` | rad/s |
| Magnetometer | `sensor_msgs/msg/MagneticField` | Tesla, converted from Android µT |
| Ambient light | `sensor_msgs/msg/Illuminance` | Lux |
| Proximity | `std_msgs/msg/Float64` | Centimetres; often only near/far hardware data |
| Barometer | `sensor_msgs/msg/FluidPressure` | Pa, converted from Android hPa |
| Rotation vector | `sensor_msgs/msg/Imu` | Android fused orientation; acceleration and gyro marked unavailable |
| Each front/back/external camera reported by Android | `sensor_msgs/msg/CompressedImage` | Continuous YUV capture encoded as JPEG, normally up to 640×480 at 0.2–30 fps; 15 fps default |

Camera capture requires the Android camera permission and only starts after
the user selects Publish. Images stream directly to ROS; the app does not save
photos to the phone. Camera calibration, camera-info publishing, microphone,
speaker subscribers and unsupported device-specific sensors are later work.

Sensor headers use `phone_sensor_frame`: Android device axes (x right, y toward
the top edge, z out of the display), independent of display rotation. No robot
mounting TF is inferred. Each camera uses its own `<camera_id>_optical_frame`.
No TF or calibration is supplied. Android rotation-vector orientation is a
device/world estimate, not a calibrated robot pose.

Sensor event monotonic timestamps are mapped to wall time using an offset
captured at publisher start. Camera timestamps use the sensor capture clock,
mapped from elapsed realtime to epoch time on devices that report a REALTIME
clock source. Other camera clocks are anchored to first arrival and marked
approximate in the camera status. This does not synchronize phone and PC clocks.
Publisher rates are caps; sensor hardware, scheduling and transport affect
actual received rates. Standard sensor publishers use best-effort, volatile
QoS. Missing estimates use message-specific unavailable conventions.

## Live camera and performance

Open **Publishers → Cameras**, choose front/back, set the maximum rate (15 fps
by default, up to 30), and Publish. The camera status separates acquired-frame
FPS, successful local ROS-publish FPS, pipeline drops, rate skips and average
JPEG encoding time. Camera hardware can run faster than the requested publish
rate; rate skips are deliberate. Pipeline drops count this app's bounded queues,
not every frame the camera HAL or network may discard.

The previous 1 fps default migrates to 15 fps once on upgrade. Other saved rates
and topic names are preserved. One camera is active at a time. No camera image
is written to storage. The current app has no in-app viewfinder; use the PC viewer:

```bash
source /opt/ros/jazzy/setup.bash
python3 tools/pc-camera-viewer.py
```

For the front camera:

```bash
python3 tools/pc-camera-viewer.py --topic /phone/camera_front_1/image/compressed
```

The viewer shows received FPS and closes with Q or its window close button.
It subscribes directly to JPEG CompressedImage using sensor-data QoS, avoiding
raw/compressed transport and reliable/best-effort mismatches. Camera IDs and
topics can differ on another phone; substitute the configured topic.

For a measured run, including verification that every received JPEG decodes:

```bash
python3 tools/pc-camera-benchmark.py --duration 30 --min-fps 15 --decode
```

This reports received FPS, payload bandwidth, invalid images and interarrival
gaps. It saves no pixels and does not claim synchronized end-to-end latency.
If the PC has multiple interfaces, isolate a chosen IP using the existing
Fast DDS profile helper (replace PC_USB_IP with the actual PC-side address):

```bash
mkdir -p device-logs
python3 tools/fastdds-interface-profile.py PC_USB_IP device-logs/camera-fastdds.xml
FASTRTPS_DEFAULT_PROFILES_FILE="$PWD/device-logs/camera-fastdds.xml" python3 tools/pc-camera-viewer.py
```

This profile affects only that command. Configure the phone's matching USB IP
and PC discovery peer in Connection, then restart the session. Hardware, camera
exposure, Wi-Fi and thermals affect achieved FPS; 30 fps is a requested maximum.

## Subscribers

1. Open **Subscribers → Display / debug text**.
2. Edit the topic, or choose a discovered `std_msgs/msg/String` topic.
3. Tap **Subscribe**.
4. Send text from the PC. The latest text and received UI-update count appear
   on the phone. Up to 4,096 bytes of the latest message are shown. Intermediate
   messages may be replaced when several arrive between UI polls.

Display QoS is reliable and volatile. It is a debug display, not a durable log.

## Network and USB

For Wi-Fi, connect phone and PC to the same reachable LAN. In **Connection**,
choose the same ROS domain as the PC (default `0`). The node namespace defaults
to `/phone`; topic names are absolute and do not automatically change when the
node namespace changes.

Explicit PC and phone IPv4 fields help when multicast discovery or automatic
interface selection does not work. Leave them blank for automatic selection.
Stop all endpoints before changing the connection profile.

For USB, enable **USB tethering** on the phone. USB debugging alone does not
provide the ROS network link. Read the USB IPv4 addresses from the app's
Connection tab and the PC's `ip -brief address`, and use them in the profile.
When both Wi-Fi and USB are up, select the phone's USB address explicitly to
use that interface. Stop/restart the session when changing paths; automatic
transport failover is not implemented.

If Realme changes USB modes and ADB reports insufficient permissions, run the
reviewable PC helper once:

```bash
sudo bash tools/setup-adb-udev.sh
```

Then restart the ADB server. The helper installs a vendor-specific udev rule
for Realme (`22d9`) on the PC; it changes no phone files.

## Monitor from the PC

Open a new terminal (Jazzy is sourced by this PC's `.bashrc`), or run
`source /opt/ros/jazzy/setup.bash`. Use the same domain as the app:

```bash
export ROS_DOMAIN_ID=0
ros2 topic list -t
ros2 topic echo /phone/imu --qos-reliability best_effort
```

In another terminal:

```bash
ros2 topic hz /phone/imu
ros2 topic info /phone/imu --verbose
ros2 topic pub --rate 1 /phone/display/text std_msgs/msg/String "{data: 'Hello from the PC'}"
```

Replace these names if you changed them in the app. Press Ctrl+C to stop each
monitor or publisher. Topics exist only while their endpoints are active;
discovery can retain a disconnected participant briefly.

## Lifecycle and verification

The app keeps the screen awake while it is visible. A foreground service owns
active sessions, so leaving the screen or recreating the Activity does not stop
publishing. The UI reconnects to the same session when reopened. Use **Stop all /
disconnect**, or **Stop** in the runtime notification, to release the complete
session, hardware, multicast and CPU wake resources. A partial wake lock does not
force the screen on outside the app. Process death/reboot does not automatically
restart capture. Screen-off and vendor power behavior need device-specific tests.

See [camera/service verification](verification/2026-10-25-camera-service.md) for
the current development build and [original v0.1 evidence](verification/2026-10-24-v01.md)
for the earlier implementation.
