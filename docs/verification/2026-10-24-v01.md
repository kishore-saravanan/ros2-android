# v0.1 verification — 2026-10-24

## Reference combination

- Realme RMX2085, Android 12 / API 31, ARM64.
- Android NDK r27c; SDK 35; Kotlin 2.2.21; AGP 8.7.3; Gradle 8.9.
- Phone: native ROS 2 Jazzy `rcl`, Cyclone DDS, introspection C/C++ typesupport.
- PC: installed Jazzy, `rclpy`, Fast DDS (`rmw_fastrtps_cpp`).
- 23 source repositories pinned; 68 packages cross-built; 69 ARM64 ROS shared
  libraries staged, plus the app library and shared NDK C++ runtime.
- Runtime revision pins and patches are in `native/`.

## Wi-Fi round trip — passed

The device test created a real `/phone/imu` publisher and a
`/phone/display/text` subscriber. It registered the phone's actual accelerometer
and gyroscope through `SensorPublishers`. The PC probe subscribed with sensor
QoS and only sent the expected display response after receiving actual IMU data.
The device asserted receipt of the exact response and a positive publish count.

The completed PC probe recorded 66 received IMU messages and 358 response
publishes over its full observation window. These are counts, not a throughput
or latency benchmark. The first sample contained real acceleration and angular
velocity with frame ID `phone_sensor_frame` and orientation marked unavailable.

## USB round trip — passed

The user enabled USB tethering. Linux assigned an IPv4 address to the new RNDIS
interface. The phone runtime was explicitly configured to its `rndis0` IPv4
address and the PC's USB IPv4 address. The PC Fast DDS participant used a custom
UDP transport with an interface whitelist containing only its USB address.
This excluded the PC's Wi-Fi transport from the test while Wi-Fi remained up.

The same actual-sensor/expected-response test passed. The PC probe recorded
4 IMU messages and 129 response publishes over its observation window. The
device ended capture once the exact expected response arrived. This establishes
both directions over USB IP, not a sustained-rate or reconnect benchmark.

Switching USB mode initially removed ADB access because the new USB product ID
lacked Linux permissions. The user ran the reviewable `setup-adb-udev.sh` helper
locally with sudo. The Realme-only rule was verified, and restarting the ADB
server restored access. No phone data or security settings were changed.

## Automated checks

- Six JVM tests passed for namespaces, domain limits, absolute topics and rates.
- Device checks passed for JNI loading, a moving native clock, real sensor
  delivery/stop, native endpoint creation and repeated session shutdown/restart.
- The endpoint UI test edited an IMU topic and rate, started an actual native
  publisher, observed its sent counter, and verified editing locks until Stop.
- The PC interoperability test is opt-in; it is intentionally skipped by the
  default device-test command and was explicitly enabled for each transport.
- Android lint completed without errors; prototype localization and coverage
  warnings remain in the generated lint report.

Raw reports and device screenshots remain in ignored build/cache directories.
No sensitive personal phone files or apps are part of these tests.

## Not established by these results

Other phone models/Android releases, calibrated IMU accuracy, synchronized
camera/sensor clocks, sustained throughput, background capture, automatic
network failover, and MCU/micro-ROS Agent operation are not established.
Camera results and final UI observations follow below.

## Front and back camera ROS publishing — passed

The user granted Robot Brain camera access through Android's permission prompt.
An explicit opt-in physical-device test selected the reported back and front
cameras in sequence, created their native ROS publishers, captured actual JPEG
frames with Camera2, and asserted at least five successful publishes per camera.
Camera capture was stopped and released before switching to the other camera.

A PC probe, restricted to the USB interface, independently received:

| Topic | First frame bytes | Frame ID | Valid JPEG messages observed |
| --- | --- | --- | --- |
| `/phone/camera_back_0/image/compressed` | 11,428 | `camera_0_optical_frame` | 9 |
| `/phone/camera_front_1/image/compressed` | 21,103 | `camera_1_optical_frame` | 3 |

Both were `sensor_msgs/msg/CompressedImage`, format `jpeg`. The PC checked JPEG
start/end markers; this is transport/payload verification, not an image-quality
or calibration assessment. Image contents were not displayed or retained, and
no image files were saved on the phone. The probe ended after observing at least
three valid frames from each camera. The device test passed and released camera
and ROS resources.

## Final regression follow-up

- The USB IMU/text round trip passed again with `USB verified ✓ 🤖`, verifying
  the native UTF-8-to-Java text conversion with non-ASCII characters.
- The native ROS graph test initially queried immediately after endpoint
  creation and raced asynchronous graph discovery. It now waits up to three
  seconds for the expected typed topic. The targeted create/discover/restart
  test then passed twice within its repeat loop.
- The edited-topic UI publisher test passed with the current sensor scheduler.
- Six JVM tests and Android lint passed. All six physical-device test methods
  have passed in their applicable runs; camera and PC round-trip tests require
  explicit opt-in arguments and external PC observers.
- Camera capture and ROS endpoints were released after tests. The app is left
  open for user-selected publishing rather than continuing camera capture.
- AGP's default device-test cleanup removed the target app after testing and
  reset its camera permission. The app was reinstalled. The project now sets
  `android.injected.androidTest.leaveApksInstalledAfterRun=true`; a targeted
  device test passed and `pm path` confirmed the app remained installed afterward.
  Realme denied programmatic permission restoration. Camera access will require
  the normal user permission prompt again on the next camera Publish; no device
  security restriction was bypassed.
